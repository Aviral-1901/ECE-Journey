# Day 54 :  Design Assertions in the ALU

## Why assertions
cocotb tests check only from outside when it runs, an assertion inside the design watches in every simulation and only checks after we write the assertion rule.

## Tool Limits
Icarus doesn't support SVA features so we did it with plain assertions inside always_comb blocks for ALU. 

## Three Assertions
Three assertions were added to alu.sv, SUB with a==b should give result=0, ADD with a=0 should give result=b, SLT output should only be 0 or 1. They all were implemented using always_comb block with if statements, asserts and $fatal.

## Proof of Firing
To check whether the assertions fired we broke the ALU (SUB doing ADD, ADD doing SUB and SLT doing ADD). On doing so the assertions fired and the error messages of the assertions were printed correctly.<br>
A failing assert in Python ends that function. While checking for ADD(while breaking the ALU), a=0 condition was first followed by a=10. After first assertion failed the function ended and the later one didn't get simulated. For first SLT test, the values were such that the result would come out to be 0 (on broken alu SLT was doing ADD) so it didn't fire the assertion but the random test did.

## $fatal vs $error
$fatal ends the whole run after an error is encountered and makes one bug look like a big failure because the later tests automatically fail after the first fail. $error keeps scope clear but cocotb still reports PASS. We kept $fatal for our assertions.

## CI Failure
The assertions worked in cocotb test for ALU but failed in final CPU integration. CI caught it because we never ran the root make test. The failing message showed fresh a,b and alu_op values next to a stale zero and result so it shows that the assertions test ran before the ALU had settled. The fix was to compile the assertions only in cocotb build with 'ifdef ALU_ASSERT and the cost is nothing watches the ALU inside the CPU.
